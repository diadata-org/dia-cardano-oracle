### Receiver funding — side-deposit + merge (Option A, from the 2026-06-05 audit)

- [x] **Contracts.** Done (2026-06-06, `d576163`): new `deposit` validator + `deposit_logic` (anti-skim: a CollectDeposit spend is valid only if the tx consumes the canonical Receiver by NFT and raises its lovelace by ≥ the full swept total — every deposit input at the shared per-client address runs the same validator instance against the same `swept` sum, so a multi-deposit skim fails every instance). Reuses the Receiver `TopUp` redeemer — **no deployed validator changes**, so the live Mainnet Receiver address is untouched. 9 inline `deposit_logic` tests (full sweep / multi-deposit credited, partial-credit skim rejected, Receiver-not-credited / lovelace-decrease rejected, no-Receiver rejected, zero-swept rejected, token-wrapped deposit must credit full ADA, `total_swept` address scoping); `aiken check` 126/0 overall.
- [x] **CLI.** Done (2026-06-06, `0111dee`): `deposit:address` / `deposit:fund` / `deposit:merge`; `makeDepositValidator`. The `deposit:merge` spends the Receiver under its `TopUp` redeemer plus the selected deposit UTxOs under `CollectDeposit`, recreating the Receiver with `balance += Σ swept` (skipping dust / native-token / datum-bearing UTxOs). The compiled deposit script + `depositValidatorHash` + `depositValidatorAddress` are persisted in the client artifact at `receiver:parameterize` / `receiver:bootstrap`, and the deposit reference script is published at `reference-scripts:publish-client` under `referenceScripts.client.deposit`. The deposit tx-build params are single-sourced and never hardcoded: `depositMinLovelace` (dust floor, default 1 ADA) + `depositMaxPerMerge` (per-merge cap, default 20) live in `config-bootstrap.json::configState`, set at `protocol:init` (`--deposit-min-lovelace` / `--deposit-max-per-merge`) — NOT in any `infrastructure.<network>.yaml`. The emulator protocol flow funds two deposits and merges them, so the deposit validator + merge run through real Plutus evaluation on every CLI test run. Wired into `run-all-cli.sh` (steps 32–35, `dec4248`) for the Preview run.
- [x] **Feeder daemon automation.** Done: the daemon auto-merges deposits as a first-class **lane task** on the SAME per-lane serial submission queue the client's oracle updates use, so a merge and an update on one Receiver can never run concurrently — mutual exclusion is structural, not a best-effort lock. The submission queue carries a discriminated `QueueEntry` (`submit` | `task`) with `enqueueTask` (`submitter/queue.ts`); the manager exposes `enqueueLaneTask(dest, run)` (`submitter/queue-manager.ts`); the daemon's `maybeAutoMergeDeposits` (`cmd/feeder/daemon-cmd.ts`) decides via the pure `shouldAutoMergeDeposits` (triggered when a Receiver drops below `receiver_balance_low_lovelace` or pending deposits reach `deposit_pending_merge_lovelace`) and dispatches the `bridge.mergeDeposits(...)` call through `enqueueLaneTask` — holding only a per-lane dedup guard (`mergeInProgress`) to collapse duplicate enqueues across refresh ticks. The old fail-safe in-flight precheck was removed; the lane queue IS the lock. The deposit floor (`depositMinLovelace`) is read from `config-bootstrap.json::configState` via `readDepositMinLovelace` — the same single source the CLI uses, not a YAML key. The pending pile per client is surfaced as the gauge `dia_bridge_cardano_deposit_pending_lovelace` (with the per-client deposit address as a label), backing the `ReceiverDepositsPending` alert. Tests: `submitter/__tests__/queue.test.ts` (a merge task and an update share one lane and never overlap), `submitter/__tests__/auto-merge-decision.test.ts` (`shouldAutoMergeDeposits`), `cmd/feeder/__tests__/deposit-floor-source.test.ts` (`readDepositMinLovelace`).

## Deferred — M3 / M4

Real future work, intentionally outside Milestone 2 (M2 is the feeder + its operational surface). Each is understood and scoped, just not started.

- [ ] **Indexer (Workstream D — M3/M4).** A read/query service the feeder does not provide today. It would expose, from the live Pair UTxOs, each pair's latest price / timestamp / nonce / signer / intent-hash; a client-level query surface (Receiver balance, subscribed pairs, accrued fees per Hook); and integration examples for Cardano dApp developers. Deferred because M2 is the write path (feeder); the consumer-facing read API is a later milestone.
- [ ] **HA / replica failover (M3/M4).** The config types carry `replica.{enabled,role,monitor_chain_id}` but nothing consumes them: no leader election, no heartbeat loop, no secondary-takeover path, no `bridge_failover_*` metrics. The feeder assumes a single instance throughout. Spectra's `internal/leader` + `internal/grpc` failover is not ported. Deferred to the HA workstream — M2 runs one instance.
- [ ] **Per-router retry policy.** Retry is global today — `createDefaultRetryPolicy` is applied uniformly to every router. Spectra allows a per-router `worker_pool.retry_policy` override; that override is not wired. Deferred — one global policy is enough for M2.
- [ ] **Distributed cron lock.** The cron re-submission service is only single-instance-safe: there is no Postgres advisory lock or leader election, so two feeder instances would double-fire the cron. Deferred until HA (depends on the leader work above).
- [ ] **Developer documentation on DIA's dev site (M4).** The operator runbook exists locally; publishing developer-facing docs on DIA's website (oracle configuration, on-chain contracts available for consumption, how to request DIA's price / real-world-asset feeds) is an M4 deliverable.
- [ ] **QA validation report + anomaly-detection evidence (M3).** The Monitoring milestone's formal QA write-up (validation results + anomaly detection) on top of the metrics/alerts that already exist. Needs a sustained live run to produce.
- [ ] **Final closeout report + video (M4).** The Catalyst closeout deliverable for the whole integration.
- [ ] **End-to-end emulator negative scenarios (extra hardening).** The on-chain adversarial cases are already covered by the 126 inline Aiken tests (see Done). What's missing is the *multi-transaction, end-to-end* layer on the Lucid emulator — scenarios that aren't expressible as a single-validator unit test: two-client parallelism, an NFT-redirect attempt spanning settle + config-update, a duplicate-live-pair race. Happy-path emulator orchestrator exists. Not gating (contracts delivered + unit-tested) — added integration hardening.

**Excluded by design — NOT pending, will never be done:** EVM gas semantics (`default_gas_limit` / `gas_multiplier` / `max_gas_price` — Cardano fees are deterministic); EVM method ABIs (`contracts.yaml::methods`); router `processing.transformations` (the validator rejects them — they would mutate the payload and break EIP-712 signature verification); `processing.validation_enabled: false` (intent-signature validation is mandatory); `processing.datasource: "processed"` (only `event` / `enrichment` are accepted).
